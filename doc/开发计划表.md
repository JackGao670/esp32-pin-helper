## 一、项目总览

### 1.1 产品定位
面向 ESP32 系列芯片（ESP32 / S2 / S3 / C2 / C3 / C5 / C6 / H2 / P4）与 ESP-IDF 工程的**可视化引脚 / 外设配置 + 硬件资源检查**工具。
- **不生成 C/C++ 代码**，只输出 `.pinconfig.json` 硬件配置文件。
- 核心壁垒：**统一芯片数据库 + 规则引擎（Validation Engine）+ Board 抽象 + 自动引脚分配 + AI 接口**。

### 1.2 技术栈
| 层级 | 技术选型 |
|------|---------|
| VS Code Extension Host | Node.js + TypeScript |
| WebView UI | React + TypeScript + Zustand（初版可降级原生 TS+CSS） |
| 样式 | 原生 CSS / Tailwind |
| 数据格式 | JSON + JSON Schema |
| 诊断集成 | VS Code Diagnostics API（Problems 面板） |

### 1.3 目录结构（目标）
```
esp-pin-planner/
├── package.json / tsconfig.json
├── src/
│   ├── extension.ts
│   ├── commands/        (openPlanner / validate / selectTarget …)
│   ├── core/
│   │   ├── model/       (配置模型、双层模型 Peripheral+Pin)
│   │   ├── validator/   (Rule Engine 8 大类规则)
│   │   ├── resolver/    (GPIO Matrix 路由解析)
│   │   └── optimizer/   (Pin 自动分配/约束求解)
│   ├── database/        (loader.ts)
│   └── vscode/          (diagnostics / configWatcher / projectDetector)
├── webview/
│   └── src/ (App / Pinout / PeripheralPanel / Inspector / Problems)
├── devices/  (芯片数据库 JSON，可独立发布为 esp-device-pack)
│   ├── esp32/ esp32s3/ esp32c3/ esp32c6/ esp32p4/
├── schemas/  (pinconfig.schema.json)
└── test/     (validator / devices 单测)
```

## 三、Phase 1 — MVP 版本（可内测）
### 3.1 目标
> 3 款目标芯片（ESP32-S3 / C6 / P4）+ P0/P1 外设 + 完整 Validation Engine + Problems 面板集成。

### 3.2 支持范围
- **芯片**：ESP32-S3（主力）、ESP32-C6（WiFi6 验证）、ESP32-P4（Camera/LCD 预验证）
- **外设优先级**：
  - **P0**：GPIO、UART（0/1/2）、I2C（0/1）、SPI（2/3）
  - **P1**：LEDC/PWM、ADC（含 ADC2 规则）、RMT、I2S
- **规则（Rule Engine）**：
  1. Pin Conflict（多分配冲突）
  2. GPIO Capability（输入/输出/开漏/模拟/RTC）
  3. Analog Conflict（ADC2 + WiFi）
  4. Strapping Pin 警告
  5. Flash / PSRAM 保留 Pin
  6. Peripheral 完整性（SPI CS 等可选信号处理）
  7. 方向检查（TX→Output / RX→Input）
  8. 特殊功能检查（USB、JTAG 固定脚）

**1. 约束建模（§3.1）**

- **决策变量**：每个（外设 type / instance / signal）槽位的 GPIO 选择
- **约束**：① 冲突——同一 GPIO 不可复用（含调用方传入的 `occupied` 已占用集）；② 能力/方向——复用 resolver 的 [`candidates()`](file:///d:/workspace/esp-pin-planer/esp32-pin-helper/src/core/resolver/peripherals.ts)，过滤 input/output/openDrain/gpio_matrix/analog；③ 板级保留——`isBoardReserved` 硬排除（仅在无其它候选时回退）
- **目标**：Warning 最少 + 首选推荐 Pin —— 通过对每个 (槽位 → GPIO) 打分实现

**2. 接口（§3.2）**（[src/core/optimizer/assign.ts](file:///d:/workspace/esp-pin-planer/esp32-pin-helper/src/core/optimizer/assign.ts)）

`recommendAssignment(peripherals, preferences?, chip?, context?) → AssignmentPlan[]`

- `peripherals`：`{ type, instance, signals? }[]`；`signals` 缺省 = definition 中的 **required** 信号（可选信号需显式列出）
- `preferences`：`avoidStrapping` / `avoidReserved` / `avoidBoardReserved` / `preferBoardDefaults` / `preferLowGpio`（默认均 true）/ `maxPlans`（默认 3）
- `context`：`{ occupied?: number[]; board?: BoardProfile }`
- 返回：按 `score` 降序去重后的 Top N；每个 plan = `{ peripherals: { owner → { type, instance, signals } }, score, warnings }`

**3. 算法**：most-constrained-first（按候选数升序排列槽位）+ 贪心 DFS + 回溯。候选按单点得分降序、每槽上限 16 个；叶子上限 `maxPlans×6`、节点上限 2×10⁵，收集多个完整方案去重后排序返回。

**4. 评分**：board 默认路由 **+50**；strapping **−100**；Flash/PSRAM **−100**；octal **−80**；USB-JTAG **−30**；板载器件误用 **−60**；低 GPIO 偏好 **−0.5×gpio**（并列时号小者优先）。偏好开关关闭则对应项不参与打分。

- **全部 GPIO 引出**：数据手册 Table 2-1 Pin Overview 的 104 脚中，GPIO0-54 共 55 个 IO 焊盘全部列出；官方规格亦明确「55 GPIOs / 55 programmable GPIOs」，故 **没有「某封装未键合某 GPIO」的情况**，`variantPins` 机制（C6 的 SiP/非 SiP 差异）在 P4 上不适用。
- **存储器不占 GPIO**：片内 flash/PSRAM 走专用 `FLASH_*` 焊盘（Table 2-1 第 27-33 脚，`VDD_FLASHIO` 域），不经 GPIO 交换矩阵，因此 `memoryPins: []` 是**正确**数据而非「未核对」——P4 上不存在 S3 那样被 Flash/PSRAM 占用的 GPIO。
- **发现并修正一处数据错误**：EV 板的 `package` 原写作 `QFN-88 (ESP32-P4)`，与数据手册不符。

## 七、风险与对策
| 风险 | 等级 | 说明 | 对策 |
|------|------|------|------|
| **芯片数据库准确性** | 🔴 高 | 手工录入出错会毁掉用户信任；每款芯片 Pin/复用规则差异极大 | ① 数据必须标注 source（TRM 章节 + ESP-IDF 版本）；② 编写 devices 单测（每个 signal 的合法 GPIO 集合抽样比对）；③ Phase 1 只做 3 款，先验证流程再批量扩 |
| **GPIO Matrix 规则** | 🟠 中 | ESP32 的 Matrix 路由比 STM32 AF 复杂；部分外设并非所有脚可 Matrix | 在 Resolver 层区分 `routing: gpio_matrix | io_mux_fixed | dedicated`，每条都要在 Database 标注 |
| **WebView 性能** | 🟡 中 | Camera 场景 20+ signal + 实时验证频繁消息 | Zustand 做局部 selector；验证 debounce；大消息用二进制或分片 |
| **ESP-IDF 兼容性** | 🟠 中 | IDF 4.x / 5.x sdkconfig 字段变化；`CONFIG_IDF_TARGET` 版本格式可能不同 | sdkconfig 解析写健壮 parser + fallback 手动选择 |
| **Scope 膨胀** | 🔴 高 | 容易变成"小 CubeMX"陷入代码生成 | **严格遵守 "不生成 C/C++ 代码" 红线**；所有复杂功能走 `.pinconfig.json` + AI 接口 |
| **工期偏差** | 🟡 中 | 数据库工作量最难估 | Phase 0 结束时对 1.1 单独做一次再评估，偏差大则砍非 P0 外设到 Phase 2 |

## 八、关键决策点（Go/No-Go 检查点）
1. **Phase 0 结束**：是否继续用 React？如 WebView 启动慢/体积大 → 降级为原生 TS+CSS。
2. **Phase 1 中期（W3）**：数据库 3 款芯片完成度 < 70% → 暂停 C6/P4，先把 S3 做深，其余推迟到 Phase 2。
3. **Phase 1 结束**：Rule Engine 8 类规则单测覆盖率 < 80% → 不进入 Phase 2，先补测试。
4. **Phase 2 结束**：Camera 配置流程在 ESP32-P4 上演示失败 → 放弃 Camera 作为 Killer Feature，主打 "Rule Engine + Board" 故事线。
5. **Phase 3 结束**：自动分配耗时 > 2s 或成功率 < 90% → Phase 4 降级为 "半手动推荐"，不追求全自动。
