ESP32 Pin Configurator
VS Code MCU 引脚配置与硬件资源检查插件技术设计方案
1. 项目定位
项目暂定名称：
ESP Pin Planner

VS Code Marketplace 名称可以考虑：
ESP32 Pin Planner
ESP-IDF Pin Configurator
ESP Hardware Config

核心定位：
一个运行在 VS Code 中、面向 ESP32 系列芯片和 ESP-IDF 工程的可视化引脚/外设配置与硬件资源检查工具。

它不生成 C/C++ 代码。
核心解决的问题：
ESP32 芯片
     ↓
Pin / Peripheral 配置
     ↓
可视化
     ↓
资源冲突检查
     ↓
电气属性检查
     ↓
ESP-IDF 约束检查
     ↓
生成配置文件

9. GPIO 数据模型
我建议不要简单：
GPIO0 → ADC

而是：
{
  "id": "GPIO0",

  "capabilities": {
    "input": true,
    "output": true,
    "openDrain": true,
    "analog": true,
    "rtc": true
  },

  "restrictions": {
    "strapping": true,
    "flash": false,
    "psram": false
  },

  "functions": []
}

这样以后才能支持复杂检查。
10. ESP32 和 STM32 最大的区别：GPIO Matrix
这是你的插件必须重点设计的。
STM32：
Pin
 ↓
AF
 ↓
Peripheral

ESP32 很多情况下：
Peripheral
      ↓
 GPIO Matrix
      ↓
 GPIO

所以模型应该支持：
Peripheral Signal
        ↓
   Routing Rule
        ↓
      GPIO

例如：
UART1_TX
   ↓
GPIO Matrix
   ↓
GPIO17

而不是简单：
GPIO17 = UART1_TX

这会让你的数据库模型更通用。
11. Peripheral Signal 模型
例如：
{
  "peripheral": "UART1",
  "signals": [
    {
      "id": "TX",
      "direction": "output",
      "routing": "gpio_matrix"
    },
    {
      "id": "RX",
      "direction": "input",
      "routing": "gpio_matrix"
    }
  ]
}

这样：
UART1_TX → GPIO17
UART1_RX → GPIO18

就是一组 Assignment。
12. 配置模型
我建议你的最终配置文件不要直接模拟 ESP-IDF 的 sdkconfig。
因为：
sdkconfig 是软件配置，不是 Pin Configuration。

建议自己定义：
.pinconfig.json

例如：
{
  "schema": "esp-pin-config/v1",

  "target": {
    "chip": "esp32s3"
  },

  "pins": [
    {
      "gpio": 17,
      "function": "UART1_TX"
    },
    {
      "gpio": 18,
      "function": "UART1_RX"
    }
  ]
}

13. Peripheral 配置
进一步：
{
  "peripherals": [

      "instance": 1,

        "TX": 17,
        "RX": 18
      }

这样比单纯记录 GPIO 更好。

20. Validation Engine
这是整个系统第二核心。
建议建立：
Rule Engine

规则：
interface ValidationRule {
    id: string;

    severity:
        | "error"
        | "warning"
        | "info";

    check(
        context: ValidationContext
    ): ValidationResult[];
}

21. 第一类规则：Pin Conflict
GPIO17

UART1_TX
SPI2_MOSI

如果同时：
UART1_TX → GPIO17
SPI2_MOSI → GPIO17

则：
ERROR
GPIO17 has multiple assignments

22. 第二类：GPIO Capability
例如：
GPIO34

某些 ESP32：
Input only

如果：
GPIO34 → LED

则：
❌ GPIO34 cannot be used as output

23. 第三类：Analog Conflict
例如：
ADC
+
WiFi

根据具体芯片规则：
⚠ ADC2 channel unavailable while WiFi is active

这个必须做成芯片/SDK版本相关规则，不要写死成全 ESP32 通用规则。
24. 第四类：Strapping Pin
例如：
GPIO0
GPIO45
GPIO46

如果属于特定芯片的启动配置相关 Pin：
⚠ GPIO0 is a strapping pin

Using this pin may affect boot behavior.

注意：
不应该一看到 Strapping Pin 就报 ERROR。

应该：
WARNING

并给出解释。
25. 第五类：Flash / PSRAM 保留 Pin
这是 ESP32 插件非常重要的一类。
如果用户选择：
ESP32-S3 + Octal PSRAM

那么对应 GPIO：
Flash/PSRAM reserved

应该：
❌ GPIOxx is reserved by PSRAM

这类检查必须和：
Chip Variant
Flash Mode
PSRAM Mode
Package

联动。
26. 第六类：Peripheral 完整性
例如：
SPI2

MOSI ✓
MISO ✓
SCLK ✓
CS  ✕

显示：
⚠ SPI2 CS is not assigned

不过这里要允许：
CS managed by software

所以：
INFO
CS not required by hardware configuration

这体现出 Rule Engine 不能简单“机械报错”。
27. 第七类：方向检查
例如：
UART_TX

必须：
GPIO output

而：
UART_RX

必须：
GPIO input

如果：
RX → Input only

反而应该：
✓

28. 第八类：特殊功能检查
例如：
USB D+
USB D-

应该：
USB peripheral

而不是普通：
GPIO

类似：
MIPI
USB
Flash
PSRAM
JTAG
USB Serial/JTAG

都可以建立特殊资源约束。

49. 一个很重要的产品原则
我建议你从一开始就坚持：

.pinconfig.json
